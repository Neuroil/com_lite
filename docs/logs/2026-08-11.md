## 1. 并发收发改造（commit 3b33143）

### 1.1 背景

改造前是单线程同步收发原型（baseline `c38115f` 快照）：阻塞收发串行，收消息期间
无法输入。改造为**收线程 + 主线程 UI** 两线程模型：Winsock 允许跨线程操作同一 socket，
内核负责串行化——收线程独占 `recv()`，主线程独占 `send()` 与 `shutdown()`。

### 1.2 线程模型

- **收线程**（`recv_loop`，operation.h:205-273）：阻塞 `recv` 循环，超时片
  `kRecvTickMs = 500ms`（operation.h:47）；`take_frame` 分帧 → `Decoder::decode` →
  `InboundQueue::push`。线程私有缓冲 `acc`/`frame`/`chunk`。退出条件：`stop` 置位、
  EOF、RST、缓冲/帧超限、解码/recv 错误。
- **主线程**（main.cpp:120-163）：`drain_inbound` 排空队列分类打印 → `std::cin` 读
  to/content → 发送前复查连接状态 → 生成 id、写 `PendingMap`、发送。UI 刷新点只在
  每次输入提示前（stdin 阻塞不可中断）。
- **InboundQueue**（operation.h:149）：收 → 主唯一共享通道，满 256 丢最旧 +
  `dropped_` 计数；`mutex_` 保护。

### 1.3 登录

`pre_login` 重构走完整分帧管线（operation.h:278）：阻塞收恰好一帧 + 残留完整帧入队 /
残帧丢弃。失败**无限重试**（q 退出）——服务端登录失败不杀连接（决策 6，main.cpp:94
注释）。收线程在登录成功后才启动（main.cpp:117-118），避免双线程抢收。

### 1.4 关停

统一清理块（ocp#2，main.cpp:165-175）：`stop` 置位 → `shutdown(SD_BOTH)` → `join` →
`closesocket` → `WSACleanup`。

### 1.5 死代码清理

删 6 死常量、5 死函数；`kServerAddress` 转正（baseline 中调用点被注释、硬编码
`"127.0.0.1"`，本次恢复使用常量 `129.211.215.72`）；`SO_KEEPALIVE`；`set_recv_timeout`
改毫秒签名。

### 1.6 线程所有权（改造后核心约束）

| 数据 | 收线程 | 主线程 | 同步 |
| --- | --- | --- | --- |
| `InboundQueue` | `push` | `pop`/`size`；dropped 读取清零 | `mutex_` |
| `stop` / `state`（atomic） | 读 / 写 | 写 / 读 | atomic |
| `PendingMap pending` | **严禁触碰**（operation.h:203-204 注释） | 读写（主线程独占） | 无锁 |
| `acc`/`frame`/`chunk` | 独占 | — | 线程私有 |
| socket fd | `recv` | `send` / `shutdown` | 内核串行化 |

## 4. bug：Ctrl+C 退出崩溃（TextBuffer is destroyed）

档案：`.agents/work-memory/knowledge/bugs/2026-08-11-textbuffer-destroyed.md`。

### 4.1 症状

Ctrl+C 退出**必现**崩溃 `TextBuffer is destroyed`（TextBuffer.guard 在 `_destroyed`
时 throw），进程 exit 1，非干净退出。

### 4.2 根因

三层因果：DESTROY 回调先于组件树销毁执行（`finalizeDestroy` 顺序：
`cleanupBeforeDestroy` → `emit("destroy")` → `destroyRecursively`）× 微/宏任务时序
（`client.close()` 的 rejectAll 把收帧循环 await 续体排**微任务**，`setImmediate(exit)`
排**宏任务**，微任务必然先 drain）× 库缺陷（TextRenderable.set content **无**
isDestroyed 守卫，destroy 后写 UI 从静默 no-op 变成 throw）。崩溃点是收帧循环退出后
的 `appendLine("[system] connection closed")`（main.ts:139→93）。

### 4.3 修复

- `src/main.ts`：模块级 `uiDead` 标志，DESTROY 回调置位；`appendLine` 开头守卫；
  新增 `setStatus` 收口替换全部 4 处 `statusText.content = ...` 写入；keypress/ENTER
  回调防御性守卫。
- `src/client.ts`：实例级 `closed` 标志，`close()` 置位；`connect()` await 续体检查
  `closed` 则 `socket.end()` 并 return（堵僵尸连接：Ctrl+C 时 connect 微任务续体可能
  先于 setImmediate 执行并复活 `this.socket`）。
- 验证：修复前必现崩溃；修复后多次 Ctrl+C 干净退出（exit 0），终端恢复。

### 4.4 上游查证

- **PR #882**（anomalyco/opentui，merged 2026-06-25）"fix(core): guard lifecycle
  passes loop against destroyed renderables"——官方对该崩溃的唯一合并修复，只改生命周期
  循环，**未覆盖 set content 路径**（0.5.1 发布于 8-04 晚于该 PR，命中路径仍无守卫）。
- **opencode #34083**（open）同款真实世界崩溃（setProp→setDefaultFg→guard）。
- **#1355**（open，2026-08-11）"exitHandler destroys the renderer but never exits"——
  同 exit 路径的相反症状（不崩、不死）。
- 官方立场：写入点加 isDestroyed 守卫即可（#882 作者实测）——与本次应用层守卫方向一致。

### 4.5 中文消息编码修复（追加，下午）

**症状**：TUI 发送中文消息后客户端完全无法收发（阻塞），服务端打印 `Client
disconnected` 掉线；英文正常。

**根因**：`protocol.ts` 的 `encodeFrame` 用 UTF-16 码元数（`serialized.length`）
做帧体缓冲分配、`body_len` 写入与 65530 校验。JS `string.length` 是 UTF-16 码元：
ASCII 1 码元 = 1 字节，中文 1 码元 = 3 UTF-8 字节。`TextEncoder.encodeInto` 写满
缓冲即在码点边界静默截断（不抛错），返回值未检查 → 中文帧体截断 + `body_len`
偏小 → 服务端按 `body_len` 切出非法/不完整 JSON → parse 失败 → 协议违约即断开
（core.cpp fatal → close_client → main.cpp:38 Disconnect）。英文纯 ASCII 码元数
= 字节数所以正常。

**修复**（protocol.ts:80-97）：先 `new TextEncoder().encode(serialized)` 拿完整
UTF-8 字节，缓冲分配 / `body_len` / 65530 上限全部改用 `bytes.length`（与 C++
`encoder.h` 的 `serialized.size()` 字节语义对齐）；用 `encode()` 替代 `encodeInto`
消灭"返回值未检查"整类错误。decode 侧（takeFrame/decodeFrame）本就是字节语义，未动。

**验证**：英文冒烟回归正常；中文验证脚本（`你好，世界！中文测试 hello 混合`）
self-echo 逐字还原 + delivered；TUI 端到端连续两条中文（`中文测试消息，能通吗`、
`第二条，服务端没断吧`）本地即时显示、连接持续存活（修复前发中文即断开）。

**横向与上游**：横向搜索同类问题 0 处（encodeFrame 是全库唯一码元/字节错配点；
C++ 侧 std::string 即字节容器结构上不可复现；四端 65530 校验现已统一字节语义）。
WHATWG 规范确认 encodeInto 码点边界截断是 per-spec 行为、read=UTF-16 码元 /
written=字节（非库缺陷）；MDN 确认 UTF-8 缓冲区间 [len, len*3]、CJK≈3 倍；
bun 实现与规范一致。修复采用规范推荐做法（encode() 拿字节数组）。

**沉淀**：knowledge/bugs/2026-08-11-chinese-message-blocks.md；system 档案
opentui-prototype.md 追加"协议层长度语义必须是 UTF-8 字节"注意事项。
